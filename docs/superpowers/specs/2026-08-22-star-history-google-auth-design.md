# 스타 히스토리 복구 및 Google 즐겨찾기 동기화 설계

- 상태: 사용자 승인 완료 (2026-08-22)
- 작성일: 2026-08-22
- 대상: `nowwcastle-sudo/github-trending-daily`
- 구현 원칙: `ponytail full` — 현재 정적 GitHub Pages 구조와 기존 렌더링을 유지하고, 보안·데이터 손실 방지·접근성은 단순화하지 않는다.

## 1. 목적

현재 대시보드의 깨진 외부 Star History 이미지를 실제로 읽을 수 있는 스타 추이 그래프로 교체하고, 브라우저에만 남아 있는 즐겨찾기를 같은 Google 계정에서 기기 간 동기화한다.

완료 상태는 다음과 같다.

1. 외부 `api.star-history.com` 호출 없이 각 카드에 스타 추이가 나타난다.
2. 과거 데이터가 있는 저장소는 과거 월별 추이와 오늘의 GitHub 총 스타 수를 함께 보여준다.
3. 과거 데이터가 없는 저장소도 대시보드가 관측한 날부터 추이를 누적한다.
4. 비로그인 즐겨찾기는 현재 브라우저에 유지된다.
5. Google 로그인 후에는 같은 계정의 즐겨찾기가 다른 브라우저·기기에도 동기화된다.
6. 다른 사용자의 즐겨찾기는 읽거나 변경할 수 없다.

## 2. 현재 상태와 확인된 원인

### 스타 히스토리

현재 `index.html`은 카드마다 `https://api.star-history.com/svg?...` 이미지를 삽입한다. GitHub가 2026-06-30 이후 stargazers 목록과 시점을 저장소 관리자·협업자에게만 공개하면서, 이 API는 임의 저장소의 그래프 대신 제한 안내 SVG를 HTTP 200으로 반환한다. `onerror`는 실행되지 않으므로 화면 코드는 실패를 정상 그래프로 오판한다.

OSS Insight의 공개 API를 현재 목록 46개에 실측한 결과, 46개 모두 HTTP 200이었고 44개는 둘 이상의 월별 지점을 반환했다. `apache/maka`, `jundot/omlx` 두 저장소는 과거 지점이 없었다. OSS Insight 값은 GH Archive의 공개 `WatchEvent` 기반 추정치이므로 언스타, 장애, 저장소 이전·비공개 전환 때문에 GitHub 현재 총계와 차이가 날 수 있다.

### 즐겨찾기와 코드 리뷰

현재 즐겨찾기는 `localStorage`의 `gh-favs` 한 키에만 저장된다. GitHub PR, 리뷰 승인, 테스트 파일은 없고 Pages 배포 작업만 존재한다.

실제 브라우저 검토에서 즐겨찾기 버튼도 기간 버튼의 상위 클릭 핸들러에 들어가 `setPeriod(undefined)`가 호출되고, `moveThumb()`이 존재하지 않는 버튼의 `offsetWidth`를 읽어 `TypeError`를 내는 결함을 재현했다. 화면 표시와 내부 `favOnly` 상태가 달라지므로 로그인 동기화 전에 이 이벤트 경계를 바로잡는다.

## 3. 범위에서 제외하는 것

- GitHub가 제한한 임의 저장소의 stargazer 신원·정확한 전체 시점을 우회 수집하지 않는다.
- 이메일/비밀번호, GitHub, Apple 등 Google 이외 로그인 제공자를 추가하지 않는다.
- 사용자 프로필, 즐겨찾기 공유, 알림, 추천 기능을 만들지 않는다.
- Next.js, React, Auth.js 또는 별도 애플리케이션 서버로 이전하지 않는다.
- Star History용 차트 라이브러리를 추가하지 않는다.
- Firebase에 사용자 이메일·표시 이름·프로필 사진을 별도 저장하지 않는다.

## 4. 전체 구조

```text
OSS Insight API ──(GitHub Actions, 1일 1회)──> star-history.json
                                                     │
index.html의 현재 GitHub 총 스타 수 ────────────────┤
                                                     ▼
GitHub Pages ──(파일 1회 로드)──> 기존 인라인 SVG 스파크라인

Google OAuth ──> Firebase Authentication ──> 사용자 UID
                                                   │
비로그인 localStorage ──(최초 1회 합집합)───────────┤
                                                   ▼
                              Cloud Firestore users/{uid}
```

정적 페이지는 그대로 유지한다. 스타 히스토리는 배포된 JSON 한 파일만 읽고, 로그인은 Firebase 공식 브라우저 모듈이 담당한다. 별도 백엔드 서버와 비밀 OAuth 클라이언트 시크릿은 저장소에 두지 않는다.

## 5. 스타 히스토리 설계

### 5.1 데이터 생성

Node.js 표준 `fetch`, `fs`, `JSON` 기능만 쓰는 작은 갱신 스크립트를 둔다. 스크립트는 다음 순서로 동작한다.

1. `index.html`의 `REPOS` 배열에서 현재 화면에 실제로 쓰는 `slug`와 `stars`를 읽는다.
2. 각 slug의 OSS Insight stargazers history를 순차 요청한다. 46개 요청은 공식 시간당 600회 제한 안에 있으며 순차 처리는 불필요한 동시 부하를 피한다.
3. 응답이 HTTP 200인지, `data.rows`가 배열인지, 날짜와 숫자가 유효한지 검사한다.
4. 월별 과거 지점을 날짜순으로 정렬·중복 제거한다.
5. 기존 `star-history.json`에 저장된 자체 일별 지점과 오늘의 정확한 `REPOS.stars` 값을 합친다.
6. 특정 OSS Insight 요청이 실패하면 그 저장소의 기존 캐시를 보존한다. 전체 파일을 빈 결과로 덮어쓰지 않는다.
7. 결과가 실제로 달라졌을 때만 파일을 갱신한다.

외부 응답은 신뢰 경계이므로 저장소당 지점 수와 문자열 길이를 제한하고, 예상하지 못한 필드는 버린다.

### 5.2 자동 갱신

GitHub Actions는 다음 세 경우에만 실행한다.

- `index.html`이 main에 push됐을 때
- 하루 한 번 03:30 KST(전날 18:30 UTC) 예약 실행
- 사용자가 수동 실행했을 때

작업 권한은 `contents: write`만 부여한다. `star-history.json`만 바뀐 커밋은 같은 작업을 다시 호출하지 않도록 push 경로를 `index.html`로 제한한다. 동시에 두 실행이 겹치지 않도록 하나의 concurrency group을 사용한다. API 실패로 새 데이터가 없으면 커밋하지 않는다.

### 5.3 브라우저 표시

페이지는 `star-history.json`을 한 번만 가져와 slug별 Map으로 만든다. 기존 `sparkline()`을 재사용해 인라인 SVG를 그린다.

- OSS Insight 지점이 둘 이상이면 과거 월별 추이를 표시한다.
- 자체 지점만 둘 이상이면 관측 시작일 이후 추이를 표시한다.
- 지점이 하나면 선을 꾸미지 않고 `관측 데이터 1일`이라고 표시한다.
- JSON 로드 실패 시 카드와 검색은 그대로 작동하며 `스타 추이를 불러오지 못했어요`라고 표시한다.
- 그래프 설명은 `GH Archive 기반 과거 추정 · 현재 총 스타는 GitHub 기준`으로 고정한다.
- `api.star-history.com` 이미지와 성공처럼 보이는 200 안내 SVG 처리는 제거한다.

## 6. Google 로그인 및 즐겨찾기 설계

### 6.1 Firebase 구성

- 요금제: 결제 수단을 연결하지 않는 Spark
- Authentication 제공자: Google만 활성화
- 승인 도메인: `nowwcastle-sudo.github.io`
- Firestore 위치: `asia-northeast3`(서울), 생성 후 변경하지 않음
- 프로덕션 SDK: Firebase 공식 브라우저 모듈 `12.17.1` 고정 버전
- 로그인 흐름: 사용자 클릭에서 시작하는 `signInWithPopup()`
- 인증 지속성: Firebase Web SDK 기본 `LOCAL`

Firebase 웹 설정 객체의 API 키는 프로젝트 식별용 공개 설정으로 저장소에 포함할 수 있다. OAuth 클라이언트 시크릿, 서비스 계정 키, Admin SDK 자격 증명은 저장소와 브라우저에 넣지 않는다.

### 6.2 Firestore 데이터

사용자마다 문서 하나만 둔다.

```text
users/{uid}
  favorites: string[]
  updatedAt: server timestamp
```

즐겨찾기는 중복 없는 `owner/repository` 문자열 배열이며 최대 500개로 제한한다. UI는 읽을 때도 문자열·slug 형식을 다시 검사해 손상된 값은 버린다. 동시 기기 추가·삭제에는 Firestore의 원자적 배열 연산을 사용한다.

### 6.3 Security Rules

규칙은 다음 불변식을 강제한다.

1. 인증된 사용자의 `request.auth.uid`와 경로의 `{uid}`가 같을 때만 읽기·쓰기를 허용한다.
2. 비로그인 요청과 다른 UID 요청은 거부한다.
3. 허용 필드는 `favorites`, `updatedAt`뿐이다.
4. `favorites`는 list이고 500개 이하여야 한다.
5. 삭제도 본인 문서만 허용한다.

규칙은 저장소의 `firestore.rules`를 정본으로 두고 Firebase Emulator에서 자동 테스트한 뒤 배포한다. 콘솔에서만 고쳐 코드와 규칙이 갈라지게 하지 않는다.

### 6.4 로컬 저장소와 최초 병합

키를 역할별로 분리한다.

- `gh-favs`: 기존 버전 호환용 입력 키
- `gh-favs-guest`: 비로그인 즐겨찾기
- `gh-favs-cache:<uid>`: 해당 계정의 마지막 정상 동기화 캐시
- `gh-favs-imported:<uid>`: 비로그인 목록의 최초 병합 완료 표시

흐름은 다음과 같다.

1. 새 버전 첫 실행에서 `gh-favs-guest`가 없으면 기존 `gh-favs`를 검증해 한 번 옮긴다.
2. 비로그인 상태에서는 `gh-favs-guest`만 읽고 쓴다.
3. Google 로그인 후 해당 UID의 Firestore 문서와 계정 캐시를 읽는다.
4. `gh-favs-imported:<uid>`가 없으면 guest와 cloud의 합집합을 한 번만 Firestore에 쓴다.
5. 클라우드 쓰기가 성공한 뒤에만 import 완료 표시를 남긴다.
6. 이후에는 클라우드 문서가 계정 즐겨찾기의 정본이다. 계정별 로컬 캐시는 오프라인 표시용으로만 갱신한다.
7. 로그아웃하면 클라우드 구독을 해제하고 `gh-favs-guest` 화면으로 돌아간다. 계정 목록을 guest에 복사하지 않는다.

이 방식은 첫 로그인 때 기존 즐겨찾기를 잃지 않으면서, 사용자가 클라우드에서 삭제한 항목이 다음 로그인 때 guest에서 다시 살아나는 것을 막는다.

### 6.5 UI와 오류 처리

헤더에 Google 로그인 버튼 하나를 추가한다. 로그인 후에는 표시 이름 또는 프로필 사진을 인증 상태 표시용으로만 사용하고 Firestore에 복사하지 않는다. 로그아웃 버튼을 함께 제공한다.

- Firebase SDK 로드나 초기화가 실패하면 기존 비로그인 즐겨찾기는 계속 작동한다.
- 팝업 차단·취소·네트워크 오류를 서로 구분한 짧은 메시지로 알린다.
- 클라우드 즐겨찾기 변경은 먼저 화면에 반영하되, 서버가 명시적으로 거부하면 이전 상태로 되돌린다.
- 오프라인 pending write는 계정 캐시에 표시하고 재연결 시 Firestore가 동기화하게 한다.
- 로그인 중이거나 동기화 상태가 결정되기 전에는 잘못된 저장소에 쓰지 않도록 즐겨찾기 버튼을 잠시 비활성화한다.
- 로그아웃과 계정 전환 때 이전 UID의 snapshot listener를 반드시 해제한다.

App Check는 기능 배포와 Security Rules 검증이 끝난 뒤 reCAPTCHA Enterprise 공급자를 monitor 상태로 연결한다. 실제 로그인과 읽기·쓰기 요청이 정상으로 집계되는 것을 확인한 후 Firestore enforcement를 켠다. 확인 없이 먼저 강제해 정상 사용자를 차단하지 않는다.

## 7. 기존 즐겨찾기 필터 결함 수정

기간 선택 위임 핸들러는 `[data-period]`가 있는 버튼만 처리한다. 즐겨찾기 버튼은 자신의 핸들러만 거치며 `period`를 변경하지 않는다. `moveThumb()`은 선택 버튼이 없을 때 조용히 계속하지 않고 테스트에서 실패하게 해 상태 결함을 숨기지 않는다.

수정 전 브라우저 재현을 자동 또는 반자동 회귀 검사로 남긴다.

1. 즐겨찾기 하나를 저장한다.
2. 즐겨찾기 필터를 켜면 카드 한 개와 `aria-pressed=true`가 일치한다.
3. 검색어를 입력해도 필터가 유지된다.
4. 필터를 다시 누르면 전체 목록으로 돌아간다.
5. 콘솔에 `offsetWidth` TypeError가 없어야 한다.

## 8. 검증과 코드 리뷰 게이트

모든 구현은 `ponytail full`로 가장 작은 동작 단위를 만든 뒤, 다음 게이트를 순서대로 통과한다.

### 8.1 스타 히스토리

- 정상 OSS Insight fixture를 월별 지점으로 변환한다.
- 깨진 JSON, HTTP 실패, 빈 rows에서 기존 캐시를 보존한다.
- 과거 추정값과 오늘 정확값을 날짜순으로 합치고 중복 제거한다.
- 44개 과거 데이터 저장소와 2개 fallback 저장소가 모두 렌더된다.
- 라이브 페이지 네트워크에 `api.star-history.com` 요청이 0건이다.
- 의도적으로 응답 검증 또는 캐시 보존 로직을 깨뜨리면 테스트가 실패한다.
- 구현 직후 `engineering:code-review`로 정확성·외부 입력·성능·실패 처리·테스트 누락을 검토한다.

### 8.2 인증·즐겨찾기

- 기존 `gh-favs`가 guest로 한 번만 이전된다.
- 첫 로그인은 guest와 cloud를 합치고, 두 번째 로그인은 재병합하지 않는다.
- 클라우드에서 삭제한 항목이 재로그인 때 복원되지 않는다.
- 로그아웃은 guest 목록으로 돌아가고 계정 목록을 유출하지 않는다.
- 쓰기 거부 시 UI가 이전 상태로 돌아간다.
- Emulator에서 본인 접근 허용, 비로그인·다른 UID 접근 거부, 허용되지 않은 필드·500개 초과 거부를 검증한다.
- 규칙에서 UID 비교를 의도적으로 제거하면 보안 테스트가 실패한다.
- 구현 직후 `engineering:code-review`로 OAuth 흐름·권한·토큰 취급·계정 전환·레이스·테스트 누락을 검토한다.

### 8.3 통합·실환경

- 기존 전체/기간/언어/검색/README/테마 기능을 브라우저에서 회귀 검사한다.
- 실제 Google 테스트 계정으로 로그인, 새로고침, 다른 브라우저 프로필 동기화, 로그아웃을 확인한다.
- Firebase 구성에는 공개 웹 설정만 있고 비밀값이 없는지 staged diff를 스캔한다.
- README 한국어·영문 사용 방법을 계정 동기화 동작에 맞게 함께 갱신한다.
- 최종 diff 전체에 `engineering:code-review`를 다시 적용한다.
- Critical/High 리뷰 발견이 0이고, Medium 발견은 수정되거나 명시적 근거와 함께 제외돼야 배포한다.
- Pages 배포 성공과 라이브 사이트 동작을 독립적으로 확인한다.

실제 Google 계정 선택과 동의는 사용자만 수행한다. 자동화는 Firebase Emulator까지만 담당하며 실계정 비밀번호·토큰을 출력하거나 저장하지 않는다.

## 9. 배포와 되돌리기

배포 순서는 Security Rules 테스트·배포, Firebase 웹 구성 연결, 기능 코드 배포, 실제 계정 검증, App Check monitor, 마지막으로 enforcement다. 인증 기능이 준비되기 전에 로그인 버튼을 노출하지 않는다.

문제가 생기면 다음 순서로 되돌린다.

1. 코드 커밋을 새 revert 커밋으로 되돌려 기존 localStorage 즐겨찾기로 복귀한다.
2. 필요하면 Firebase Google 제공자를 비활성화한다.
3. Firestore Rules를 deny-all로 배포해 데이터 접근을 차단한다.
4. 기존 Firestore 데이터는 자동 삭제하지 않는다. 삭제가 필요하면 범위와 복구 가능성을 확인하고 사용자가 별도로 승인한다.
5. 스타 히스토리 JSON 생성이 실패해도 마지막 정상 파일을 유지한다.

## 10. 선택한 것과 버린 것

- Firebase Auth + Firestore를 선택했다. 정적 사이트를 유지하면서 Google 로그인과 사용자별 보안 규칙을 공식 SDK로 해결하기 때문이다.
- Supabase는 SQL 확장성이 현재 요구보다 크고 Google OAuth·RLS 설정 대상이 더 많아 제외했다.
- Auth.js는 서버 프레임워크 이전이 필요해 제외했다.
- Star History 토큰 방식은 타인 소유 트렌딩 저장소에 권한을 주지 못하므로 제외했다.
- 브라우저에서 OSS Insight를 카드 수만큼 직접 호출하는 방식은 방문자별 rate limit·지연·외부 장애를 전가하므로 제외했다.
- 과거 데이터를 포기하고 오늘부터만 수집하는 방식은 즉시 복구 가능한 44개 저장소의 과거 신호를 버리므로 보조 fallback으로만 사용한다.

## 11. 뒤집는 조건

- GitHub가 임의 공개 저장소의 stargazer 시점을 공식 API로 다시 제공하면 OSS Insight 추정 구간을 공식 데이터로 교체한다.
- OSS Insight의 성공률 또는 최신성이 지속적으로 기준을 충족하지 못하면 과거 추정 수집을 중단하고 자체 일별 관측만 유지한다.
- 즐겨찾기를 넘어 사용자 데이터와 복잡한 관계형 질의가 실제 요구되면 Supabase 또는 별도 백엔드를 새 ADR로 재검토한다.
- Firebase 비용·정책·가용성이 운영 기준을 벗어나면 사용자 데이터 내보내기 후 대체 저장소를 검토한다.
