## 다음 세션이 먼저 답할 질문

GitHub Trending Daily가 사용자에게 더 편하고 더 유용한 정보를 주려면 무엇을 다음 기능으로 채택해야 하는가? 비슷한 서비스의 실제 기능과 GitHub Trending 사용자들의 반복 요구를 근거로 후보를 선별하되, 지금 단계에서는 기능을 구현하지 말고 우선순위가 있는 조사 보고서와 권고안을 먼저 제시한다.

## 사용자가 요청한 다음 작업

1. GitHub Trending Daily와 성격이 비슷한 저장소·서비스를 찾아 실제 제공 기능을 조사한다.
2. `web-collect`, Exa, `agentbrowser`를 사용해 GitHub Trending 공식 기능에 사용자들이 평소 바라는 개선점을 2차 조사한다.
3. 유사 서비스에서 발견한 기능, 사용자 요구에서 발견한 기능, 조사자가 독립적으로 판단한 기능을 출처별 섹션으로 나눈다.
4. 후보를 중복 제거해 하나의 우선순위표로 합치고, 사용자 이용 편의성과 정보 유용성을 가장 중요한 평가축으로 삼는다.
5. 먼저 조사 보고서와 권고안을 사용자에게 제시한다. 기능 구현과 README 수정은 이 권고안에 대한 사용자 확인 뒤 진행한다.

## 사용자가 이미 제시한 기능 방향

### 1차 구현 후보

- 사이드바: 첫 구성 요소는 로그인과 즐겨찾기다. 현재 상단에 있는 인증·동기화·즐겨찾기 경험을 어떻게 옮기거나 연결할지 조사 결과와 함께 제안한다.
- 분야별 필터: 기존 언어 필터에 더해 저장소의 용도·분야로 거르는 기능이다. 사용자가 예로 든 분류는 `MCP`, `플러그인 & 스킬`, `AI Agent`, `라이브러리 & 프레임워크`, `IDE & ADE`, `편의성 기능`, `기타`다.
- 분야 분류는 사용자 예시를 그대로 확정하지 말고, 유사 서비스와 실제 Trending 표본을 대조해 빠진 범주·겹치는 범주·명칭을 제안한다.

### 후순위 후보

- 개인화 추천: 앞선 기능과 조사에서 채택된 저비용 기능을 먼저 구현한 뒤 검토한다.
- 비용 분담 방안: 이용자의 LLM API 키 사용 또는 Codex·Claude Code 같은 AI 도구와의 OAuth 연동 가능성을 조사한다.
- 위 방안은 구현 가능하다고 가정하지 않는다. 제공자 약관, OAuth 공개 지원 여부, 토큰 위임 범위, 정적 사이트에서의 키 노출, 과금 오남용, 저장 위치를 공식 문서로 확인해야 한다.
- 브라우저에 LLM 키나 CLI 인증 토큰을 평문 저장하는 방식은 기본안으로 제안하지 않는다. 안전한 구현에 백엔드 프록시가 필요하다면 운영비와 복잡성을 비용표에 포함한다.

## 조사 범위와 증거 기준

### A. 유사 저장소·서비스 조사

- GitHub Trending을 보완·보존·분석·개인화하는 오픈소스 저장소와 공개 서비스를 찾는다.
- 단순한 이름 유사성이 아니라 실제 작동 화면, README, 문서, 최근 유지보수 상태를 확인한다.
- 각 대상에서 `탐색`, `필터`, `랭킹`, `변화 추적`, `개인화`, `알림`, `내보내기`, `접근성` 기능을 확인한다.
- 기능이 README에만 적혀 있고 실제로 작동하는지 확인할 수 없으면 `문서상 제공`으로 구분한다.
- 최근성은 조사 시점의 저장소 활동·릴리스·사이트 상태를 다시 확인한다. 이 핸드오프의 날짜를 최신 근거로 쓰지 않는다.

### B. 사용자 요구 조사

- GitHub 공식 문서·공식 커뮤니티·GitHub Discussions 또는 공개 이슈를 우선한다.
- 이후 Reddit, Hacker News, 개발자 블로그, 포럼 등에서 반복되는 불편과 요청을 교차 확인한다.
- 검색 결과 수나 단일 댓글을 수요로 과장하지 않는다. 서로 독립적인 출처에서 반복되는 요구인지 구분한다.
- 직접 인용은 최소화하고, 요구를 요약한 뒤 원문 링크와 날짜를 붙인다.
- `web-collect`, Exa, `agentbrowser`가 실제로 호출 가능하지 않으면 없는 결과를 꾸미지 말고 사용하지 못한 도구와 대체 수집 경로를 보고한다.

### C. 독립 판단

- 유사 서비스나 사용자 글에 직접 등장하지 않아도 현재 사이트 구조·데이터로 실현 가능하고 효용이 높은 후보를 별도 섹션에 제안한다.
- 관측 사실과 조사자의 추론을 섞지 않고 `근거에서 발견`과 `독립 제안`을 표시한다.
- 기능 수를 늘리는 것보다 사용자가 더 빨리 유용한 저장소를 발견하고, 변화의 의미를 더 정확히 이해하게 하는지를 우선한다.

## README 개편 요구사항

조사 보고서의 로드맵을 사용자가 확인한 뒤 `README.md`와 `README.en.md`를 함께 개편한다.

1. 문서 초입에 환영 문구와 짧은 홍보 문장을 둔다.
2. 실제 배포 페이지의 작동 장면 스크린샷 1~2개를 저장소 안의 안정된 경로에 넣는다. 로컬 감사 폴더 경로를 README에 직접 연결하지 않는다.
3. 제작 배경을 적는다.
4. 현재 기능은 한 기능당 한 줄로 설명한다. 누구나 알 것 같은 기능도 생략하지 않고, 여러 기능을 한 줄에 합치지 않는다.
5. 추가 예정 기능도 한 기능당 한 줄로 `기능명 - 무슨 기능인지` 형식으로 적는다.
6. 사용 방법을 적는다.
7. 사이트 링크는 문서에서 즉시 눈에 띄도록 큰 제목과 굵은 링크로 표시한다.
8. 한국어판과 영문판의 정보 구조·기능 목록·로드맵이 서로 어긋나지 않게 대조한다.
9. 스크린샷은 개편 후 실제 production 화면을 새로 촬영하고, 밝은 화면과 좁은 화면 중 사이트의 장점이 잘 드러나는 조합을 선택한다.

## 이미 완료되어 재구현하지 않을 것

사용자는 2026-08-26 실제 페이지에서 아래 항목이 모두 의도대로 작동한다고 확인했다.

- 반응형 툴팁: 측면 공간이 충분하면 카드 목록이 움직이지 않고, 부족한 경우에만 필요한 픽셀만큼 왼쪽으로 이동한다.
- 모션: 카드 너비를 흔들지 않는 transform 기반 이동과 reduced-motion 처리가 적용됐다.
- 갱신 주기: 워크플로와 화면 문구가 2시간 간격, 서울 기준 홀수 시 07분으로 일치한다.
- 배지 안내: 연속 등장, 스타 변화, HOT의 의미를 항상 볼 수 있다.
- 번역 비용 게이트: 신규 저장소 또는 README SHA-256이 바뀐 저장소만 LLM 번역 대상으로 보낸다.

7. 기능 후보를 평가표와 단계별 로드맵으로 정리해 사용자에게 한 번에 제시한다.
8. 여기서 멈추고 사용자의 채택·기각·보류 결정을 기다린다.
9. 승인 뒤 사이드바·분야 필터 설계를 확정하고 테스트부터 구현한다.
10. 확정된 로드맵을 반영해 한국어·영문 README와 production 스크린샷을 개편한다.

## 완료 정의

다음 조사 세션은 아래 조건을 만족해야 첫 라운드가 완료된다.

- 실제로 확인한 유사 서비스와 기능이 출처 링크·확인일과 함께 정리됐다.
- 사용자 요구가 단일 의견과 반복 요구로 구분됐다.

- 독립 제안이 조사 사실과 분리됐다.

- 즉시·다음·나중·기각의 권고와 이유가 있다.
- 구현이나 README 편집은 사용자 승인 전 시작하지 않았다.
